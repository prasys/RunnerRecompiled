# RunnerRecompiled — чек-лист

Нативный порт Mirror's Edge (Xbox 360) на Android ARM64 статической перекомпиляцией. Устройство разработки — Lenovo Y700 Gen4 (Snapdragon, Adreno 830).

Обновлено 2026-10-25. Галочка — проверенный результат указанного объёма, а не готовность всего порта. Полная история проверок по дням и все прежние допущения — в [CHECKLIST-ARCHIVE-2026-10-25.md](CHECKLIST-ARCHIVE-2026-10-25.md); подробности каждого шага — в [HANDOFF.md](HANDOFF.md); решения — [DECISIONS.md](DECISIONS.md).

## Где мы сейчас (2026-10-25)

- Игра запускается на планшете, проходит заставки и меню, продолжает сохранение, загружает и рисует уровень пролога; пользователь прошёл до первой главы.
- **FPS на уровне: 26–33,5 кадра/с** с правильной картинкой (на старте работы — 4–6, в начале сессии оптимизации — 0,5 в меню). Ролики и меню — 30.
- 20-минутная игра без падений; self-tests **766**, exit 0.
- Запуск пока исследовательский: отдельный нативный процесс через ADB + приложение-превью для картинки и ввода.

## Действующие допущения (правило: каждое допущение записано)

1. Записи GPU через собственный (сырой) вид памяти не считаются записями CPU — как в Xenia.
2. Окно между загрузкой текстуры в GPU и защитой страницы может пропустить запись CPU (то же окно, что в Xenia).
3. `dcbst` на виртуальных адресах в параллельном режиме не проверяет отображение (физические — проверяет по карте committed).
4. Прерывания GPU и vblank выполняются под большой блокировкой ядра.
5. Гонки данных гостевого кода ведут себя как на параллельных аппаратных потоках консоли (генерированный `stwcx` = CAS).
6. Генерированный код корректен под -O2 (долгие прогоны и 20 минут игры без падений; глубже не проверено).
7. Патчи Xenia (адреса/семантика) применимы 1:1 к этой сборке — слова инструкций по адресам проверены; после регенерации кода патчи применить заново.
8. `clear_memory_page_state` выключен по умолчанию: write watch и инвалидация при выделении памяти ловят все записи CPU. Пользователь подтвердил цвета до вертолёта; дальше по игре не проверено.
9. Декодирование XMA идёт сразу на Kick под блокировкой, без отдельного потока; качество звука по сравнению с консолью не измерялось.
10. Чтение файла игры без гейта: чтение с диска консоли не останавливает другие потоки.
11. APK: загрузка `libmeruntime.so` (`System.load`) из приватной `files/` приложения разрешена при targetSdk 35 — проверено на Y700 (Android планшета); на других прошивках не проверено.
12. APK: `VK_SUBOPTIMAL_KHR` при повороте игнорируется (поворачивает композитор; стоимость поворота не измерена); на fold-устройствах смена размера ловится сравнением размера окна.
13. Сигнальные обработчики runtime (SIGSEGV write watch, SIGALRM/SIGUSR1 снапшоты) работают в процессе приложения рядом с ART — проверено 300-секундным маршрутом до уровня.
14. Вторая очередь graphics-семейства (только для present) не мешает CP: blit идёт в очередь 0 после работы CP, а очередь 1 только ждёт семафор и показывает кадр. Проверено 4 прогонами до уровня на Adreno 830.
15. Пауза APK: удержание большой блокировки ядра останавливает всех гостевых потоков на ближайшем вызове ядра; время гостя идёт дальше (после паузы — один длинный кадр). Проверено двумя паузами в меню/интро; длинные паузы на уровне не проверены.
16. Хранилище пайплайнов RexGlue и `VkPipelineCache` из файла корректны на Adreno 830: повреждённый или несовместимый кэш пересоздаётся пустым. Не проверено на устройстве.
17. Барьеры `sync`/`lwsync`/`eieio` как `__atomic_thread_fence` (SEQ_CST / ACQ_REL) достаточны для публикации данных между гостевыми потоками на ARM; обычные загрузки и сохранения кода игры не атомарны. Проверяется переходом в Edge.
18. Достижения хранятся только в памяти на время сессии; при следующем запуске их нет (как будто не получены).
19. exp_adjust выборки текстур читается из слова 3 константы (биты 13:18), как в Xenia Canary 02d2cb5 и `xenos.h`; RexGlue v0.10.0 читал слово 4. Перевод шейдеров идёт заново при каждом запуске (хранилище держит только guest-ucode), поэтому старый кэш исправлению не мешает. `ME_FETCH_EXP_WORD4=1` — старое поведение для A/B.
20. Глубина D24S8 на любом GPU Adreno (vendor 0x5143, и Qualcomm, и Turnip) хранится как D32_SFLOAT_S8: round trip D24 на Adreno 830 неточен (проверено: на Turnip с D24 в первом тайле MSAA нули освещения, с D32 — 0).
21. oDepth пиксельного шейдера при host RT и D24FS8 масштабируется в host [0, 0.5] (×0.5), как в DXBC-трансляторе Xenia; растеризованная глубина остаётся float32 (не 20e4) — ноги на пути MSAA без патча из-за этого мерцают, режим ME_DEPTH24_PS=1 убирает мерцание ног, но портит один тайл.
22. Геймпады (`Controller.java`): семейство — по vendor id (0x054C Sony, 0x057E Nintendo, 0x045E Microsoft). Правый стик — RX/RY, если у пада нет Z/RZ или нет осей триггеров (тогда Z/RZ считаются триггерами); иначе Z/RZ. Кнопки L2/R2 как события клавиш дают полный LT/RT только у падов без осей триггеров. Кнопки Nintendo по умолчанию — по положению (Android standard mapping), обмен A↔B / X↔Y — в меню паузы на модель пада. Ни на одном PS/Switch паде не проверено.
23. Складное устройство = есть `android.hardware.sensor.hinge_angle`; «сложено» = smallestScreenWidthDp < 600. На раскладушках (Flip) уведомление будет показываться при каждом запуске (оно не блокирует, 7 с, тап скрывает). Jetpack WindowManager не используется (сборка без Gradle). Не проверено на реальном Fold.
24. (Кандидат, не включено по умолчанию) `ME_HOST_DEPTH_STORE=0`: при смене владельца EDRAM глубина переносится через 24-битную кодировку Xbox без отдельной float32-копии хоста; точность глубины между проходами как на консоли, а не выше. Снимки совпадают; визуальная проверка игрой не завершена.
25. (Кандидат) `ME_HOIST_UPLOADS=1`: выгрузка страниц shared memory, которых в текущей отправке ещё не касалась ни одна записанная команда (чтение, выгрузка, запись GPU), выполняется в начале отправки. Предполагается, что все обращения GPU к shared memory проходят через RequestRanges/RangeWrittenByGpu; отладочные прямые копии буфера (ME_DIAGNOSTIC_*) это не учитывают.

30. (2026-11-01) Слот адресного пространства (PCR/TLS/стек) завершённого потока отдаётся новому, если на поток нет ссылок ObReferenceObjectByHandle; память слота обнуляется как свежая. Предполагается, что игра не обращается к KTHREAD/TLS/стеку завершённого потока по старым адресам без такой ссылки. Handle старого потока остаётся рабочим (ожидание — «завершён»). Путь переиспользования самотестом не покрыт.
31. (2026-11-02) `ME_OCCLUSION_ASYNC=1` (по умолчанию; `=0` — прежняя схема с разрывом прохода на каждый запрос): пул запросов делится на 4 части по 2048, по одной на отправку команд (сброс в начале, копия результатов в конце, вне проходов). Предполагается, что сегментов запросов в одной отправке не больше 2048 (иначе этот запрос получает фиктивный ответ, счётчик async_overflow) и что результаты отправки читаются до того, как её часть пула переиспользуется через 4 отправки. Гость по-прежнему получает реальный счёт по завершении отправки. Режим `=2` (мгновенный ответ из кэша по адресу структуры) **неверен**: игра гоняет ≈1300 структур по кругу на ≈520 запросов за кадр, адрес не равен объекту → всё моргало (пользователь, 2026-11-02); оставлен только как эксперимент.

35. (2026-11-02, PC-лифтер, `pc/LIFTER-DESIGN.md`) Достижимость по релокациям: код, на который не указывает ни одна релокация и ни один относительный переход из достижимого кода, считается мёртвым и не поднимается (49 117 функций, 2,16 МБ). Предполагается, что `.reloc` полна и игра не вычисляет адреса кода арифметикой (база + смещение). Если такое встретится, поднятый код сработает как ловушка с адресом в диспетчере косвенных вызовов.
36. (2026-11-02, PC-лифтер) Затравка из данных (релокации), чей код не декодируется или выходит за `.text`, считается данными и отбрасывается вместе со всем, что из неё найдено (195 затравок). Затравки из `call` и SafeSEH считаются кодом всегда.
37. (2026-11-02, PC-лифтер) Флаг направления DF всегда 0: в достижимом коде exe нет `std`/`cld`. Строковые инструкции поднимаются только вперёд. Флаг AF не моделируется (`lahf`/`pushfd` дают AF=0): в коде нет `daa`/`aaa`, кроме недостижимых или единичных мест, которые станут ловушкой.
38. (2026-11-02, PC-лифтер) Модель возврата: `ret` в поднятом коде возвращает управление вызвавшей C-функции и не читает адрес со стека. Это верно для функций, в которые входят через `call`. Для входов из релокаций (блоки `__except`, обработчики SEH, середины функций) это не так: на стенде 14 таких «функций» уходят по `ret` в случайный адрес. Их семантику задаст рантайм SEH (этап 3).
39. (2026-11-02, PC-лифтер) Оптимизированный C выбрасывает загрузки, результат которых не используется. Исходный код на таких чтениях может упасть, поднятый — нет (2 функции на стенде; на -O0 совпадают). Предполагается, что игра не полагается на сбой чтения вне `__try`.
40. (2026-11-02, стенд) Поднятый код на стенде собирается с `-mllvm -fast-isel`: clang 23.1.3 i686 SelectionDAG неверно компилирует `(x & 0xFFFFFF00) | zext(load8)` (IR верный). Для ARM64-сборки обход не нужен (проверено на AArch64 — `and`+`orr` на месте). Если сменится версия clang, проверить заново.
41. (2026-11-02, PC-лифтер) x87 моделируется на `double`. Показатель уже, чем у 80-битного x87: промежуточные значения ниже ≈2,2e-308 или выше ≈1e308 x87 хранит нормальными, а `double` — денормализованными, нулём или бесконечностью. Режим 64-битной точности не моделируется. При 24-битной точности (D3D9) результат сначала округляется до 53 бит, потом до 24 — изредка это даёт отличие в последнем бите (двойное округление). Предполагается, что игра не опирается на такие величины и на последний бит. На стенде это 3 функции из 2 219 с плавающей точкой: сходимость ряда, выход промежуточного значения за диапазон, `fsin` около π.
42. (2026-11-02, PC-лифтер) Не моделируются флаги исключений x87 и SSE (младший байт `fnstsw`, биты 0–5 MXCSR) и бит C1. Предполагается, что игра проверяет только C0/C2/C3 (`test ah, 0x41/0x44/0x05`). `rsqrtss`/`rcpss` дают точное значение вместо 12-битного приближения железа. Трансцендентные функции считаются через libm, последние биты отличаются от микрокода x87 (особенно `fsin` около кратных π).
43. (2026-11-02, PC-лифтер) Значения NaN: x86 выдаёт отрицательный «неопределённый» NaN (`0xFFC00000`/`0xFFF8…`), ARM по умолчанию — положительный. На стенде (x86) это не проверить. Предполагается, что игра не смотрит на биты NaN. MMX-регистры хранятся отдельно от x87: совпадают только теги, но не значения.
